# Especificación: 004 - Preparación para Producción, Despliegue en la Nube y Estándar de Portafolio

**Estado:** Borrador  
**Fecha:** 2026-11-16  

## 1. Propósito y Contexto
- **Qué**: Preparación integral, estandarización de portabilidad y documentación de la plataforma de comercio electrónico **Afrolash** para su puesta en producción real utilizando exclusivamente infraestructura y servicios en la nube 100% gratuitos (Vercel o Netlify para la SPA React 19, Render Web Services para la API REST Node.js/Express 5, Aiven for MySQL o TiDB Serverless para la base de datos relacional MySQL 8 cifrada con TLS/SSL, Stripe en modo de prueba y Gmail SMTP), asegurando al mismo tiempo su presentación como proyecto de portafolio profesional de alto nivel y preservando de manera intacta el flujo de desarrollo y pruebas en el entorno local.
- **Por qué**: Tras implementar el sistema de diseño editorial cosmético (Spec 002) y robustecer la seguridad integral bajo OWASP Top 10 (Spec 003), Afrolash requiere eliminar acoplamientos rígidos al entorno de desarrollo local (como URLs fijas a `http://localhost:5000` en componentes cliente, ausencia de servido público de imágenes dinámicas en backend, y falta de soporte SSL para bases de datos en la nube), solventar la deuda técnica de inconsistencia de mayúsculas/minúsculas en consultas SQL para servidores MySQL sobre Linux (`lower_case_table_names=0`), proveer endpoints de monitoreo de salud (`/api/health`), generar scripts SQL reproducibles de esquema y datos semilla de demostración, y documentar la arquitectura y despliegue para que reclutadores, evaluadores técnicos y el propio equipo puedan desplegar, auditar y mantener la solución en la nube sin incurrir en costos operativos.

## 2. Requisitos Funcionales (EARS)

### RF-01: Parametrización de API, Carga de Recursos Multimedia y Enrutamiento SPA en Frontend
- **RF-01.1 (Requisito Ubicuo)**: El cliente web DEBERÁ resolver de forma dinámica la dirección URL base de la API REST a través de la variable de configuración `REACT_APP_API_URL`, normalizando su valor mediante la eliminación de espacios en blanco y barras diagonales finales redundantes.
- **RF-01.2 (Comportamiento No Deseado / Error)**: SI la variable de configuración `REACT_APP_API_URL` no está definida o contiene una cadena vacía en el entorno de ejecución, ENTONCES el cliente web DEBERÁ asumir automáticamente la dirección `http://localhost:5000` como valor por defecto, preservando la compatibilidad inmediata con el entorno de desarrollo local y con las suites de pruebas automatizadas.
- **RF-01.3 (Requisito Guiado por Evento)**: CUANDO el cliente web procese rutas de imágenes de productos del catálogo, el sistema DEBERÁ resolver determinísticamente la dirección URL final conforme a las siguientes reglas:
  1. SI la ruta es nula, vacía o no corresponde a una cadena de texto, ENTONCES el sistema DEBERÁ retornar una cadena vacía (`''`).
  2. SI la ruta ya corresponde a una dirección URL absoluta (con prefijos `http://` o `https://`) o a un esquema de datos en línea (`data:`), ENTONCES el sistema DEBERÁ retornarla inalterada.
  3. SI la ruta corresponde a una ruta relativa de catálogo (comenzando por `/img/` o `img/`), ENTONCES el sistema DEBERÁ normalizar el prefijo y anteponer incondicionalmente la URL base resuelta de la API (`REACT_APP_API_URL` o `http://localhost:5000` por defecto), garantizando la ausencia de barras diagonales dobles (`//`) en la concatenación.
  Los activos estáticos propios del shell visual de la SPA (tales como logotipos o fondos locales del frontend) deberán resolverse exclusivamente desde el origen del propio frontend.
- **RF-01.4 (Requisito Ubicuo)**: El sistema DEBERÁ documentar en `client/.env.example` todas las variables de entorno requeridas por el cliente web (`REACT_APP_API_URL`, `REACT_APP_STRIPE_PUBLISHABLE_KEY`), incluyendo comentarios explicativos sobre el respaldo automático a `http://localhost:5000` cuando `REACT_APP_API_URL` se omite o permanece vacía, y DEBERÁ incluir reglas de reescritura de rutas para servidores de alojamiento estático (archivo `_redirects` en `client/public/` o configuración equivalente), garantizando que las recargas de página y el acceso directo a rutas con parámetros (tales como enlaces de recuperación de contraseña `/?vista=restablecer&id=...&token=...`) respondan con código HTTP `200 OK` entregando la aplicación sin emitir errores `404 Not Found`.

### RF-02: Servicio Estático de Imágenes en Backend, Soporte de Proxy Inverso y Carga Segura de Entorno
- **RF-02.1 (Requisito Ubicuo)**: La API Express DEBERÁ exponer de manera pública y estática el directorio de almacenamiento de imágenes bajo la ruta `/img`, emitiendo cabeceras de política de recursos de origen cruzado (`Cross-Origin-Resource-Policy: cross-origin`) que faculten el consumo directo de dichos activos multimedia desde aplicaciones cliente alojadas en dominios cruzados.
- **RF-02.2 (Requisito Ubicuo)**: El servidor DEBERÁ cargar y resolver sus variables de entorno de manera agnóstica a la ubicación del directorio de trabajo actual, operando idénticamente tanto si el proceso Node.js se inicia desde la raíz del monorepo como si se inicia desde el subdirectorio `server/`.
- **RF-02.3 (Requisito Guiado por Estado)**: MIENTRAS la variable de configuración `TRUST_PROXY` esté habilitada en el entorno (configurada con el valor textual `'true'` o como un entero positivo mayor o igual a 1), el servidor Express DEBERÁ habilitar la configuración de saltos de proxy inverso estableciendo el nivel numérico exacto de saltos confiables (asumiendo `1` cuando el valor sea `'true'`, correspondiente al balanceador y terminador TLS estándar en plataformas en la nube como Render), cumpliendo con las validaciones de seguridad de los limitadores de tasa y evitando configuraciones booleanas permisivas ilimitadas (`true`); y SI la variable `TRUST_PROXY` no está definida o posee el valor `'false'`, ENTONCES el servidor DEBERÁ mantener la directiva desactivada (`false`), previniendo la suplantación de direcciones IP en entornos locales sin proxy.

### RF-03: Conexión SSL Condicional a MySQL Cloud y Estandarización de Esquema para Linux
- **RF-03.1 (Requisito Guiado por Estado)**: MIENTRAS la variable de configuración `DB_SSL` esté definida como `true`, el pool de conexiones de base de datos MySQL (`mysql2/promise`) DEBERÁ negociar conexiones seguras cifradas mediante TLS/SSL, permitiendo configurar la verificación estricta de certificados a través de `DB_SSL_REJECT_UNAUTHORIZED` (con valor por defecto `false` para admitir certificados gestionados por plataformas en la nube gratuitas como Aiven o TiDB Serverless).
- **RF-03.2 (Comportamiento No Deseado / Error)**: SI la variable `DB_SSL` no está configurada o posee un valor distinto de `true`, ENTONCES el pool de conexiones DEBERÁ conectarse en modo estándar no cifrado sin requerir certificados TLS, manteniendo intacto el funcionamiento en instancias locales de MySQL sobre `localhost`.
- **RF-03.3 (Requisito Ubicuo)**: El sistema DEBERÁ estandarizar en minúsculas todos los nombres físicos de tablas utilizados en las sentencias SQL de controladores, utilidades y pruebas automatizadas del backend (`usuarios`, `productos`, `pedidos`, `detalles_pedido`, `auditoria`), garantizando la compatibilidad estricta con servidores MySQL ejecutados sobre sistemas operativos Linux (`lower_case_table_names=0`) y preservando inalterados los valores literales históricos de la columna `tabla_afectada` en los registros de auditoría (`'Pedidos'`, `'Productos'`, `'Usuarios'`).

### RF-04: Endpoint Público de Diagnóstico y Salud (`/api/health`)
- **RF-04.1 (Requisito Guiado por Evento)**: CUANDO un monitor de disponibilidad, balanceador de carga o evaluador externo envíe una petición `GET /api/health`, el sistema DEBERÁ verificar el estado operativo del servicio y la conectividad activa con el motor de base de datos MySQL ejecutando una consulta de comprobación no bloqueante (`SELECT 1`).
- **RF-04.2 (Requisito Guiado por Evento)**: CUANDO la consulta a la base de datos responda de manera exitosa y el servidor se encuentre en estado operativo, el sistema DEBERÁ responder con código de estado HTTP `200 OK` y una carga útil estructurada en formato JSON `{ "status": "ok", "database": "connected", "timestamp": "..." }`, aplicando en esta ruta una política CORS permisiva dedicada (admitiendo solicitudes provenientes de cualquier `Origin` externo o sin cabecera `Origin` para permitir monitoreos de disponibilidad y diagnósticos externos desatendidos), procesada con precedencia para no ser rechazada con código HTTP `403` por el CORS restrictivo de negocio y preservando intacta la protección CORS con respuesta `403` en todas las rutas de negocio del sistema.
- **RF-04.3 (Comportamiento No Deseado / Error)**: SI la base de datos MySQL no responde, excede el tiempo límite o rechaza la conexión, ENTONCES el sistema DEBERÁ responder de forma controlada con código de estado HTTP `503 Service Unavailable` y una carga útil estructurada en formato JSON `{ "status": "error", "database": "disconnected", "timestamp": "..." }`, absteniéndose de emitir volcados de memoria, contraseñas de conexión o trazas de depuración internas.

### RF-05: Scripts SQL Reproducibles para Despliegue Limpio
- **RF-05.1 (Requisito Ubicuo)**: El sistema DEBERÁ proporcionar en el repositorio un script SQL reproducible (`database/schema.sql`) que defina la estructura completa e idempotente de la base de datos `afrolash_db`, cumpliendo estrictamente con:
  1. Creación idempotente de la base de datos y de las 5 tablas físicas en minúsculas mediante `CREATE TABLE IF NOT EXISTS`, ordenadas estrictamente según sus dependencias de claves foráneas (`usuarios`, `productos`, `pedidos`, `detalles_pedido`, `auditoria`).
  2. Declaración de claves primarias, tipos de datos exactos, índices de optimización y restricciones de clave foránea con reglas explícitas de integridad referencial: `ON DELETE CASCADE` para `pedidos.id_usuario` referenciando a `usuarios.id_usuario` y para `detalles_pedido.id_pedido` referenciando a `pedidos.id_pedido`; y `ON DELETE RESTRICT` para `detalles_pedido.id_producto` referenciando a `productos.id_producto`.
  3. Creación idempotente de los 6 disparadores de auditoría (`trg_pedidos_update`, `trg_productos_insert`, `trg_productos_update`, `trg_productos_delete`, `trg_usuarios_update`, `trg_usuarios_delete`) precedidos por `DROP TRIGGER IF EXISTS` y encapsulados mediante bloques delimitadores estándar `DELIMITER // ... DELIMITER ;`, garantizando su ejecución limpia y reproducible en consolas interactivas MySQL CLI, Workbench y clientes web de bases de datos en la nube.
- **RF-05.2 (Requisito Ubicuo)**: El sistema DEBERÁ proporcionar un script de datos semilla (`database/seed.sql`) que pueble de forma limpia el catálogo inicial de productos cosméticos con descripciones detalladas, ingredientes, instrucciones, precios, existencias y rutas de imagen válidas, así como cuentas de usuario de demostración para los tres roles del sistema (`admin`, `empleado`, `cliente`). Las contraseñas ficticias de demostración documentadas para evaluadores DEBERÁN cumplir estrictamente con la política de seguridad establecida en la Spec 003 (mínimo 8 caracteres, al menos una letra mayúscula y al menos un dígito numérico) y sus valores almacenados en `database/seed.sql` DEBERÁN estar pre-hasheados mediante el algoritmo `bcryptjs` con un factor de costo de 10 rondas de sal, garantizando que reclutadores y evaluadores técnicos puedan iniciar sesión y probar la plataforma sin divulgar contraseñas privadas reales del desarrollador.

### RF-06: Documentación de Portafolio y Guía de Despliegue 100% Gratuito
- **RF-06.1 (Requisito Ubicuo)**: El sistema DEBERÁ proporcionar en la raíz del repositorio un archivo `README.md` exhaustivo y de presentación profesional orientado a portafolio técnico, abarcando: descripción del producto cosmético, diagrama y descripción de arquitectura full-stack desacoplada, stack tecnológico moderno (React 19, Express 5, MySQL 8), resumen de medidas de seguridad OWASP Top 10 implementadas, metodología multiagente Spec-Driven Development (SDD), instrucciones de instalación y ejecución local paso a paso, comandos de verificación y pruebas automatizadas, y sección de credenciales de demostración para evaluadores.
- **RF-06.2 (Requisito Ubicuo)**: El sistema DEBERÁ proporcionar un documento guía (`docs/deployment.md`) que detalle paso a paso el procedimiento reproducible y sin costo para desplegar la base de datos en la nube gratuita (Aiven for MySQL o TiDB Serverless), el backend API en Render Web Services y el frontend SPA en Vercel (o Netlify). La guía DEBERÁ indicar explícitamente el despliegue del servicio web en Render configurando el directorio raíz en la raíz del monorepo (`Root Directory: .`) y ejecutando los comandos con `--prefix server` (ej. `npm --prefix server install`, `npm --prefix server start`) para preservar la coherencia relativa de rutas hacia el directorio de almacenamiento `client/public/img/`; DEBERÁ documentar las variables de entorno requeridas en cada plataforma, la advertencia técnica sobre el almacenamiento de archivos efímero en los planes gratuitos de Render para nuevas imágenes subidas en tiempo de ejecución, y el flujo de integración continua para desplegar actualizaciones desde el repositorio local mediante `git push origin main`.

### RF-07: Verificación Automatizada y Cero Regresiones
- **RF-07.1 (Requisito Ubicuo)**: El sistema DEBERÁ disponer de pruebas automatizadas de integración en el backend que verifiquen el endpoint de diagnóstico `GET /api/health` (tanto en condición exitosa `200` como en condición degradada `503` simulada), el servido estático de imágenes en `/img` con cabeceras de recursos cruzados, la resolución condicional de opciones SSL en el pool de base de datos y la ejecución correcta de consultas sobre tablas en minúsculas.
- **RF-07.2 (Requisito Guiado por Evento)**: CUANDO se ejecuten las suites automatizadas de pruebas y compilación del monorepo (`npm --prefix server test`, `npm --prefix client test -- --watchAll=false`, `npm --prefix client run build` y `node --check`), el sistema DEBERÁ completar todas las pruebas en verde y finalizar la compilación con código de salida 0 y cero advertencias críticas de ESLint, garantizando la ausencia total de regresiones funcionales frente a las especificaciones 001, 002 y 003.

## 3. Casos Límite y Restricciones

1. **Resolución determinista de imágenes y assets del shell SPA**:
   - En entorno local, la SPA corre en `http://localhost:3000` y la API en `http://localhost:5000`. En producción, la SPA se ubica en un dominio estático (ej. `https://afrolash.vercel.app`) y la API en otro dominio de servicios (ej. `https://afrolash-api.onrender.com`). Para evitar errores de carga y rutas rotas, la resolución de imágenes aplica la regla determinista: valores nulos/vacíos devuelven `''`, URLs absolutas o data URIs se mantienen idénticas, y rutas relativas de catálogo (`/img/...` o `img/...`) anteponen incondicionalmente la URL base de la API normalizada (evitando dobles barras `//`). Los activos propios de la maqueta SPA (iconos, fuentes, fondos estructurales) se resuelven contra el origen del frontend estático. Las cabeceras `Cross-Origin-Resource-Policy: cross-origin` emitidas por la API permiten que el navegador consuma las imágenes sin bloqueos de aislamiento entre sitios.
2. **Filesystem efímero en planes gratuitos de nube (Render Free Tier)**:
   - Los servicios web gratuitos de Render aplican suspensión por inactividad (*spin-down* tras 15 minutos sin tráfico) y operan sobre un sistema de archivos efímero. Cada reinicio restaura el contenedor al estado de su commit en Git, por lo que imágenes subidas dinámicamente por administradores que no formen parte del repositorio se perderán al reiniciar el contenedor. La documentación y la arquitectura deben explicitar esta restricción técnica inherente a los planes gratuitos, garantizando que el catálogo inicial empaquetado en el repositorio permanezca siempre íntegro y accesible.
3. **Manejo de arranque en frío (*Cold Start*) y resiliencia de la interfaz**:
   - Los contenedores gratuitos suspendidos en Render pueden demorar entre 30 y 50 segundos en reactivarse ante la primera solicitud entrante. El endpoint `/api/health` debe ser ligero para permitir verificaciones de estado eficientes por herramientas externas, y la SPA de React debe gestionar estados visuales de carga en catálogo y login sin disparar errores fatales ni desautenticar erróneamente al usuario por demoras transitorias.
4. **Fallo de conectividad o agotamiento de conexiones en `/api/health`**:
   - Si la base de datos en la nube agota su cuota de conexiones simultáneas o presenta intermitencia de red, la consulta `GET /api/health` debe interceptar la excepción mediante un tiempo límite prudencial y emitir inmediatamente una respuesta HTTP `503 Service Unavailable` JSON, sin exponer cadenas de conexión, usuarios ni contraseñas en el cuerpo de error.
5. **Configuración de Proxy Inverso (`TRUST_PROXY`) con saltos numéricos exactos**:
   - Al alojar la API detrás de proxies de terminación TLS de Render o balanceadores cloud, habilitar `trust proxy: true` de forma booleana introduce riesgos de validación en librerías de limitación de tasa y configuraciones permisivas no auditadas. La variable `TRUST_PROXY` debe configurar el número entero exacto de saltos confiables (`1` por defecto cuando se configure `'true'`, o el número entero positivo indicado), mientras que en entornos locales sin proxy debe permanecer desactivada (`false`) para impedir suplantación de direcciones IP (*IP spoofing*) mediante cabeceras forjadas.
6. **Sensibilidad estricta a mayúsculas/minúsculas en MySQL sobre Linux**:
   - En entornos locales sobre Windows, el motor MySQL opera habitualmente con `lower_case_table_names=1` (insensible a mayúsculas). En servidores Linux (Aiven, TiDB, Render o Docker), opera con `lower_case_table_names=0` (sensible a mayúsculas). Cualquier consulta a `Productos` en lugar de `productos` resulta en error fatal `Table 'afrolash_db.Productos' doesn't exist`. La estandarización exhaustiva de todas las sentencias SQL a nombres en minúsculas elimina de raíz este riesgo de incompatibilidad.
7. **Cero credenciales privadas o secretos reales en el repositorio**:
   - Ningún script SQL (`schema.sql`, `seed.sql`), archivo de configuración o documento de despliegue debe contener credenciales personales reales, llaves privadas de Stripe de producción o contraseñas de cuentas de correo reales. Toda cuenta de demostración debe emplear identificadores ficticios documentados, y las plantillas de entorno deben utilizar valores genéricos explicativos.
8. **Restricción de alcance**:
   - Esta especificación no modifica la paleta de colores, la navegación accesible, el diseño cosmético "Rose Noir & Gold" (Spec 002) ni los mecanismos de transacciones atómicas, validación estricta y limitación de tasa ya aprobados e implementados en la Spec 003. Su alcance se circunscribe a la portabilidad hacia la nube gratuita, resolución de deuda técnica SQL y documentación con estándar de portafolio profesional.

## 4. Criterios de Aceptación

- [ ] Todas las peticiones HTTP del cliente web (`client/src/`) resuelven la URL base de la API a través de la variable `REACT_APP_API_URL`, utilizando `http://localhost:5000` como respaldo automático cuando dicha variable no esté configurada o esté vacía.
- [ ] La resolución de imágenes del catálogo aplica las reglas deterministas: cadenas nulas/vacías retornan `''`, URLs absolutas o data URIs se retornan intactas, y rutas relativas de catálogo (`/img/...` o `img/...`) anteponen la URL base resuelta de la API sin generar dobles barras diagonales (`//`).
- [ ] El archivo `client/.env.example` documenta todas las variables requeridas por el frontend (`REACT_APP_API_URL`, `REACT_APP_STRIPE_PUBLISHABLE_KEY`) con comentarios explicativos sobre el respaldo local automático, y el frontend cuenta con reglas de reescritura SPA (archivo `_redirects` en `client/public/`) que permiten recargar o acceder a enlaces profundos con parámetros sin emitir errores 404 en servidores estáticos.
- [ ] La API Express expone de forma pública y estática el directorio `/img` con cabeceras `Cross-Origin-Resource-Policy: cross-origin`, permitiendo el consumo seguro de imágenes desde dominios externos autorizados.
- [ ] El backend carga sus variables de entorno correctamente tanto al iniciarse desde la raíz del proyecto como desde el directorio `server/`.
- [ ] El servidor Express habilita de forma configurable la directiva `trust proxy` mediante la variable `TRUST_PROXY` con saltos numéricos exactos (`1` cuando valga `'true'` o el entero especificado), permaneciendo desactivada (`false`) en desarrollo local.
- [ ] El pool de conexiones MySQL (`server/config/db.js`) negocia conexiones cifradas TLS/SSL cuando `DB_SSL=true`, soportando configuración de certificados con `DB_SSL_REJECT_UNAUTHORIZED`, y opera en modo no cifrado estándar por defecto en desarrollo local.
- [ ] Todas las consultas SQL en controladores, utilidades y suites de prueba del backend utilizan exclusivamente nombres de tablas físicas en minúsculas (`usuarios`, `productos`, `pedidos`, `detalles_pedido`, `auditoria`), garantizando compatibilidad con servidores MySQL sobre Linux sin alterar los valores de auditoría existentes.
- [ ] El endpoint público `GET /api/health` cuenta con política CORS permisiva propia (admitiendo cualquier `Origin` y peticiones sin `Origin`), responde con HTTP `200 OK` JSON `{ "status": "ok", "database": "connected", ... }` cuando la conexión a MySQL está activa, y responde con HTTP `503 Service Unavailable` JSON `{ "status": "error", "database": "disconnected", ... }` de forma controlada cuando la base de datos es inalcanzable, sin debilitar el CORS restrictivo `403` de las rutas de negocio ni exponer trazas internas.
- [ ] Se dispone del archivo `database/schema.sql` con la definición DDL completa, reproducible e idempotente de la base de datos `afrolash_db`, sus 5 tablas en minúsculas ordenadas por dependencias foráneas (`usuarios`, `productos`, `pedidos`, `detalles_pedido`, `auditoria`) con `CREATE TABLE IF NOT EXISTS`, claves primarias, claves foráneas con reglas explícitas de integridad referencial (`ON DELETE CASCADE` en pedidos/detalles y `ON DELETE RESTRICT` en producto) e índices, junto a los 6 disparadores de auditoría con `DROP TRIGGER IF EXISTS` y delimitadores estándar `DELIMITER // ... DELIMITER ;`.
- [ ] Se dispone del archivo `database/seed.sql` con datos semilla iniciales limpios para el catálogo de productos y cuentas de demostración para los roles `admin`, `empleado` y `cliente` con contraseñas seguras (mínimo 8 caracteres, al menos una mayúscula y un número) pre-hasheadas con `bcryptjs` (costo 10) y credenciales ficticias documentadas.
- [ ] La raíz del monorepo cuenta con un `README.md` exhaustivo y profesional orientado a portafolio, cubriendo arquitectura, tecnologías, medidas de seguridad OWASP, metodología SDD, guía de ejecución local, comandos de prueba y credenciales de demo.
- [ ] El proyecto incluye la guía técnica `docs/deployment.md` detallando el paso a paso reproducible 100% gratuito para desplegar la base de datos en Aiven/TiDB, la API en Render (con Root Directory `.` y comandos `--prefix server`) y el frontend en Vercel/Netlify, documentando variables de entorno, la restricción de almacenamiento efímero en planes gratuitos y el flujo de actualización vía `git push origin main`.
- [ ] Se dispone de pruebas automatizadas de integración en el backend que validan el endpoint `/api/health` (estados 200 y 503), el servido estático de `/img` y la configuración SSL condicional.
