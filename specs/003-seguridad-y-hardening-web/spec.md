# Especificación: 003 - Seguridad y Hardening Web

**Estado:** Aprobado  
**Fecha:** 2026-11-16  

## 1. Propósito y Contexto
- **Qué**: Fortalecimiento integral de la seguridad web (*hardening*) y resiliencia de la plataforma de comercio electrónico **Afrolash**, abarcando la protección de cabeceras de transporte HTTP, políticas de intercambio de recursos de origen cruzado (CORS) estrictamente restringidas por entorno con denegación explícita, limitación cuantitativa de tasa de solicitudes (*rate limiting*) en endpoints críticos de autenticación, control riguroso de tamaño de carga útil y subida segura de archivos multimedia con manejo centralizado de errores y limpieza automática de archivos parciales en disco, prevención estricta de suplantación de identidad (IDOR / BOLA) y manipulación de precios (*anti-price tampering*), transaccionalidad atómica e integridad de inventario en pedidos con respuesta unívoca de conflicto por stock, preservación del modelo numérico de visibilidad de productos, validación de entradas robusta alineada entre frontend y backend con sanitización contra inyección HTML en correos salientes, auditoría de variables de entorno al arranque, y suites automatizadas de verificación de seguridad aisladas sobre puertos efímeros.
- **Por qué**: Como paso previo al despliegue de Afrolash en entornos productivos accesibles al público y para consolidar el sistema como un proyecto de portafolio de grado profesional, es imperativo mitigar riesgos tipificados en el estándar OWASP Top 10 (tales como Broken Access Control, Security Misconfiguration, Injection y Denial of Service). La implementación actual carece de cabeceras estándar de protección, utiliza una política CORS permisiva a cualquier origen sin denegación explícita, no limita cuantitativamente el ritmo de peticiones en rutas de autenticación, confía en el identificador de usuario y precios recibidos en el cuerpo para procesar órdenes, carece de transacciones atómicas que prevengan compras con inventario insuficiente o estados corruptos, muta valores numéricos de catálogo a texto, y puede emitir respuestas no estructuradas o mensajes genéricos que dificultan la sincronización con los interceptores del cliente web. Este endurecimiento asegura la integridad de los datos, la confidencialidad de los usuarios y la alta disponibilidad operativa sin alterar los flujos funcionales ni la experiencia estética previamente aprobados.

## 2. Requisitos Funcionales (EARS)

### RF-01: Cabeceras HTTP Seguras y Ocultamiento de Huella Tecnológica
- **RF-01.1 (Requisito Ubicuo)**: El sistema DEBERÁ emitir cabeceras HTTP estándar de protección en todas las respuestas de la interfaz de servicios (API), incluyendo protección contra enmarcado no autorizado en navegadores (`X-Frame-Options: DENY` o equivalente), prevención de interpretación errónea de tipos MIME (`X-Content-Type-Options: nosniff`), control de divulgación de remitentes (`Referrer-Policy: strict-origin-when-cross-origin` o equivalente), y activación de transporte estricto en conexiones seguras (`Strict-Transport-Security`).
- **RF-01.2 (Requisito Ubicuo)**: El sistema DEBERÁ suprimir u omitir de forma ubicua en toda respuesta HTTP cualquier cabecera o identificador que revele el motor, marco de trabajo o software tecnológico subyacente del servidor (como cabeceras `X-Powered-By` o firmas de software), impidiendo el perfilamiento automatizado por agentes maliciosos.
- **RF-01.3 (Requisito Guiado por Evento)**: CUANDO un cliente web autorizado solicite recursos multimedia estáticos (imágenes del catálogo de cosméticos) o datos de la API desde un origen web distinto, el sistema DEBERÁ incluir cabeceras de política de recursos de origen cruzado (`Cross-Origin-Resource-Policy: cross-origin`) que permitan la correcta visualización de dichos recursos en el navegador sin comprometer el aislamiento entre sitios.

### RF-02: Política CORS Restringida por Entorno
- **RF-02.1 (Requisito Ubicuo)**: El sistema DEBERÁ delimitar la lista de orígenes web autorizados para el consumo de la API mediante la variable de configuración de entorno designada (`FRONTEND_URL`), permitiendo un único origen o múltiples orígenes válidos separados por comas, y asumiendo por defecto el origen de desarrollo local (`http://localhost:3000`) cuando no se configure un valor explícito en dicho entorno.
- **RF-02.2 (Requisito Guiado por Evento)**: CUANDO una petición HTTP entrante contenga una cabecera de origen (`Origin`) que coincida de forma exacta con la lista de orígenes autorizados en `FRONTEND_URL`, el sistema DEBERÁ admitir la solicitud y entregar las cabeceras de control de acceso correspondientes (`Access-Control-Allow-Origin`, métodos HTTP permitidos y cabeceras autorizadas).
- **RF-02.3 (Comportamiento No Deseado / Error)**: SI una petición HTTP entrante presenta una cabecera `Origin` perteneciente a un dominio no registrado en la lista de orígenes autorizados por `FRONTEND_URL`, ENTONCES el sistema DEBERÁ omitir cualquier cabecera `Access-Control-Allow-Origin` hacia ese remitente y responder de forma inmediata con código de estado HTTP `403 Forbidden` bajo el formato JSON `{ "mensaje": "Acceso denegado por política de origen (CORS)." }` antes de ejecutar la lógica del controlador correspondiente.
- **RF-02.4 (Requisito Guiado por Evento)**: CUANDO una petición HTTP carezca de cabecera `Origin` (como solicitudes directas originadas por herramientas de pruebas de integración, utilidades de diagnóstico en línea de comandos o llamadas de servicios internos), el sistema DEBERÁ admitir y procesar la petición de acuerdo con los mecanismos de autenticación y autorización correspondientes a cada ruta, sin bloquearla por ausencia de contexto de navegador.

### RF-03: Limitación de Tasa contra Fuerza Bruta y Abuso
- **RF-03.1 (Requisito Guiado por Estado)**: MIENTRAS la API reciba peticiones dirigidas a los puntos de entrada públicos y sensibles del módulo de autenticación (inicio de sesión `/api/auth/login`, registro de cuenta `/api/auth/registro`, solicitud de recuperación de contraseña `/api/auth/recuperar-password` y confirmación de restablecimiento `/api/auth/restablecer-password/:id/:token`), el sistema DEBERÁ contabilizar el volumen de solicitudes recibidas por cada dirección IP dentro de una ventana temporal estricta de **15 minutos**.
- **RF-03.2 (Comportamiento No Deseado / Error)**: SI el número de peticiones efectuadas por una misma dirección IP hacia cualquiera de los puntos sensibles de autenticación supera el umbral máximo de **15 solicitudes** dentro de la ventana activa de 15 minutos, ENTONCES el sistema DEBERÁ bloquear de forma inmediata las solicitudes subsecuentes de dicha IP, respondiendo con código de estado HTTP `429 Too Many Requests`, cabecera informativa de tiempo de espera (`Retry-After`) y una carga útil estructurada en formato JSON `{ "mensaje": "Demasiadas solicitudes realizadas. Por favor, intente nuevamente más tarde." }`.
- **RF-03.3 (Requisito Guiado por Evento)**: CUANDO concluya la ventana temporal de 15 minutos sin que la dirección IP incurra en nuevos excesos, el sistema DEBERÁ reiniciar el contador de solicitudes y restaurar el acceso habitual a los puntos de entrada de autenticación.
- **RF-03.4 (Característica Opcional)**: DONDE la aplicación se ejecute en entorno de pruebas automatizadas (`NODE_ENV === 'test'`), el sistema DEBERÁ permitir la ejecución continua de las suites funcionales ordinarias sin bloqueos cruzados entre pruebas consecutivas, habilitando al mismo tiempo la capacidad de aislar o configurar el límite de tasa para verificar de manera determinista la respuesta HTTP `429` en la suite de seguridad.

### RF-04: Límites de Tamaño de Solicitud y Carga Segura de Archivos
- **RF-04.1 (Requisito Ubicuo)**: El sistema DEBERÁ restringir el tamaño máximo permitido del cuerpo de toda solicitud entrante codificada en formato JSON a **100 KB**, previniendo el consumo excesivo de memoria y ataques de denegación de servicio por saturación de carga útil.
- **RF-04.2 (Comportamiento No Deseado / Error)**: SI una solicitud entrante excede el límite de 100 KB para cuerpos JSON o presenta una estructura sintácticamente inválida o malformada, ENTONCES el sistema DEBERÁ capturar el error de forma centralizada y responder con código de estado HTTP `400 Bad Request` (ante sintaxis JSON malformada) o HTTP `413 Payload Too Large` (ante exceso de tamaño) bajo el formato uniforme JSON `{ "mensaje": "..." }`, suprimiendo cualquier página de error por defecto en HTML o exposición de trazas internas del servidor.
- **RF-04.3 (Requisito Guiado por Evento)**: CUANDO un usuario administrador envíe archivos adjuntos multimedia para la creación o actualización de productos en el catálogo, el sistema DEBERÁ validar que cada archivo individual no exceda el tamaño máximo de **2 MB**, que la petición no supere un límite estricto de **3 archivos en total** (fotografía principal, fotografía de instrucciones y fotografía de consejos), y que el formato corresponda exclusivamente a extensiones y tipos MIME de imagen permitidos (JPEG, JPG, PNG y WEBP).
- **RF-04.4 (Comportamiento No Deseado / Error)**: SI una solicitud de carga multimedia excede el límite de 2 MB por archivo, supera la cantidad máxima de 3 archivos admitidos, o contiene tipos MIME o extensiones no autorizadas, ENTONCES el sistema DEBERÁ rechazar la operación de forma centralizada respondiendo con código de estado HTTP `413 Payload Too Large` (si se excede el tamaño máximo por archivo) o HTTP `400 Bad Request` (si se supera la cantidad de archivos o el tipo de formato), bajo el formato uniforme JSON `{ "mensaje": "..." }`, y DEBERÁ eliminar de inmediato del sistema de archivos cualquier archivo parcial que hubiese sido escrito en disco durante el procesamiento de la solicitud abortada.

### RF-05: Prevención de Suplantación IDOR/BOLA, Anti-Price Tampering y Transaccionalidad Atómica en Pedidos
- **RF-05.1 (Requisito Guiado por Evento)**: CUANDO un cliente autenticado solicite el procesamiento de una orden de compra (`/api/pedidos/procesar`), el sistema DEBERÁ vincular el pedido de forma exclusiva e inalterable al identificador del usuario autenticado obtenido de su credencial de sesión (token verificado), descartando e ignorando cualquier identificador de usuario provisto en el cuerpo o parámetros de la petición HTTP para impedir la suplantación de identidad y vulnerabilidades de referencia directa insegura a objetos (IDOR / BOLA).
- **RF-05.2 (Comportamiento No Deseado / Error)**: SI la solicitud de procesamiento de pedido contiene un carrito de compras vacío, una estructura de carrito que no sea una lista válida, cantidades de producto no enteras o inferiores a 1, datos de contacto o envío vacíos, o referencias a productos inexistentes o marcados como no disponibles para la venta (con indicador numérico de visibilidad distinto de activo), ENTONCES el sistema DEBERÁ rechazar la solicitud con código de estado HTTP `400 Bad Request` y un mensaje estructurado en formato JSON `{ "mensaje": "..." }`.
- **RF-05.3 (Comportamiento No Deseado / Error)**: SI al evaluar la orden de compra la cantidad solicitada para cualquiera de los productos del carrito es superior a las existencias físicas actualmente disponibles en el inventario, ENTONCES el sistema DEBERÁ abortar el procesamiento de la orden, responder unívocamente con código de estado HTTP **`409 Conflict`** bajo el formato JSON `{ "mensaje": "..." }` identificando la insuficiencia de existencias, y dejar inalterados todos los registros de la base de datos.
- **RF-05.4 (Requisito Guiado por Evento)**: CUANDO se confirme la validez de los productos, existencias suficientes y los datos de envío, el sistema DEBERÁ consultar directamente desde la base de datos los precios unitarios autoritativos vigentes de cada producto y recalcular el importe total de la orden en el servidor (descartando e ignorando cualquier precio unitario o total manipulado provisto en el cuerpo de la petición), y DEBERÁ ejecutar la inserción del pedido maestro con el total recalculado por el servidor, la inserción de las líneas de detalle con los precios oficiales, la actualización de los datos de contacto del cliente y el descuento exacto de unidades en el inventario bajo una única transacción de base de datos atómica, garantizando que si cualquier paso falla se revierta íntegramente toda la operación (*rollback*) sin generar pedidos huérfanos ni existencias negativas.
- **RF-05.5 (Requisito Guiado por Estado)**: MIENTRAS el stock de un producto se reduzca a 0 tras la confirmación exitosa de un pedido, el sistema DEBERÁ representar la condición de producto agotado exclusivamente a través de la condición `stock = 0`, preservando el tipo de dato numérico del indicador de visibilidad en catálogo (`1` = visible/activo, `0` = inactivo) sin mutar su valor a cadenas de texto (como `'agotado'`) ni forzar el ocultamiento automático a `0`, permitiendo que el catálogo continúe mostrando el cosmético como sin inventario e impidiendo nuevas compras mientras el stock permanezca en 0.
- **RF-05.6 (Requisito Guiado por Evento)**: CUANDO un cliente autenticado solicite la inicialización de la pasarela de pagos (`/api/pagos/crear-intencion`), el sistema DEBERÁ validar que el importe total solicitado sea un valor numérico finito estrictamente mayor a 0 antes de comunicarse con el proveedor externo de pagos, respondiendo con código de estado HTTP `400 Bad Request` en formato JSON `{ "mensaje": "..." }` ante valores inválidos o menores o iguales a cero.

### RF-06: Validación de Entradas, Sanitización en Notificaciones y Manejo Seguro de Secretos
- **RF-06.1 (Requisito Guiado por Evento)**: CUANDO un usuario envíe datos a los puntos de registro de cuenta (`/api/auth/registro`), confirmación de restablecimiento (`/api/auth/restablecer-password/:id/:token`) o solicitud de recuperación de contraseña (`/api/auth/recuperar-password`), el sistema DEBERÁ validar estrictamente la presencia y formato de los datos antes de consultar la base de datos: validando sintaxis estándar de correo (devolviendo HTTP `400 Bad Request` JSON ante correos inválidos o vacíos en cualquiera de dichos puntos, y conservando la respuesta HTTP `200` genérica en recuperación únicamente para correos con sintaxis válida para evitar enumeración de usuarios); y exigiendo en registro y restablecimiento contraseñas de al menos 8 caracteres, al menos una letra mayúscula y al menos un número, respondiendo con HTTP `400 Bad Request` y formato JSON `{ "mensaje": "..." }` si se incumple alguna regla.
- **RF-06.2 (Requisito Guiado por Evento)**: CUANDO el sistema elabore notificaciones salientes por correo electrónico que incorporen datos suministrados por usuarios (como nombres, correos o direcciones en la bienvenida de empleados, recuperación de contraseñas o confirmaciones de facturación), el sistema DEBERÁ escapar y neutralizar todo carácter con significado sintáctico en HTML (`<`, `>`, `&`, `"`, `'`), previniendo la inyección de código malicioso o falsificación de contenido en los clientes de mensajería de los destinatarios.
- **RF-06.3 (Comportamiento No Deseado / Error)**: SI una solicitud dirigida a cualquier punto de entrada protegido presenta una credencial de autorización ausente, con formato defectuoso, manipulada criptográficamente o cuya vigencia temporal haya expirado, ENTONCES el sistema DEBERÁ responder consistentemente con código de estado HTTP `401 Unauthorized` y cuerpo JSON `{ "mensaje": "..." }`, permitiendo que el interceptor del cliente web detecte de manera unívoca la finalización de sesión y proceda al desalojo del estado local y redirección correspondiente.
- **RF-06.4 (Requisito Ubicuo)**: El sistema DEBERÁ auditar durante el arranque la presencia de las variables críticas de configuración: en entornos de operación normal y producción, la ausencia del secreto de firma JWT (`JWT_SECRET`) o de las credenciales de conexión a base de datos DEBERÁ abortar de manera explícita la inicialización del servidor registrando el motivo en consola; en entorno de pruebas automatizadas (`NODE_ENV === 'test'`), el sistema DEBERÁ admitir la inicialización sin abortar cuando se ejecuten casos de prueba unitarios o suites aisladas; y el enlace de recuperación de contraseña generado en notificaciones DEBERÁ utilizar el origen configurado en `FRONTEND_URL` con respaldo en `http://localhost:3000`, documentando todas las variables requeridas en `server/.env.example` sin exponer credenciales reales.

### RF-07: Ejecución Aislada, Desacoplamiento de Puerto y Verificación Automatizada de Seguridad
- **RF-07.1 (Requisito Ubicuo)**: El sistema DEBERÁ disponer de una suite automatizada de pruebas de integración de seguridad en el backend capaz de verificar de forma determinista la presencia de cabeceras de seguridad, el rechazo de orígenes CORS no autorizados con HTTP `403 Forbidden`, la limitación de tasa (15 solicitudes en 15 minutos con HTTP `429`), el bloqueo de cargas útiles excesivas (>100 KB JSON con HTTP `413`, >2 MB multimedia con HTTP `413`, >3 archivos con HTTP `400`), la eliminación de archivos parciales ante cargas fallidas, el control de suplantación de identidad y *anti-price tampering* en pedidos, el rechazo unívoco con HTTP `409 Conflict` por stock insuficiente, la atomicidad transaccional, y las validaciones de contraseñas y correos.
- **RF-07.2 (Requisito Guiado por Evento)**: CUANDO se ejecute la suite de verificación automatizada de seguridad, el sistema DEBERÁ desacoplar la exportación de la aplicación de la apertura del puerto de escucha de red, permitiendo que el ejecutor de pruebas opere sobre puertos efímeros en memoria sin incurrir en colisiones de enlace de puerto (`EADDRINUSE`) con servidores en ejecución, y DEBERÁ limpiar de manera garantizada los registros transaccionales creados durante los casos de prueba, preservando intactos los datos productivos y el historial de auditoría preexistente.

## 3. Casos Límite y Restricciones

1. **Concurrencia en compra simultánea del último stock disponible**:
   - Si dos o más clientes intentan adquirir concurrentemente las últimas unidades de un producto (por ejemplo, stock restante de 1 unidad y ambos clientes solicitan 1 unidad al mismo tiempo), la transacción de base de datos atómica debe aislar ambas operaciones. Una de las órdenes debe completarse con éxito y la otra debe ser rechazada de forma limpia y unívoca con HTTP `409 Conflict` por falta de existencias disponibles, impidiendo que el stock caiga en valores negativos y evitando estados inconsistentes de facturación.
2. **Tokens manipulados, truncados o expirados frente a interceptores del cliente web**:
   - Todo token con firma no válida, clave secreta incorrecta, formato no decodificable o tiempo de expiración superado debe retornar unívocamente HTTP `401 Unauthorized` con carga JSON `{ "mensaje": "..." }`. Se prohíbe el uso de estados HTTP `400` para este escenario a fin de garantizar que el interceptor de peticiones del frontend limpie la sesión en el almacenamiento local y redirija al usuario al flujo de inicio de sesión de forma predecible.
3. **Cargas útiles malformadas, cuerpos excesivos y limpieza de archivos parciales en disco**:
   - Peticiones con cuerpos JSON truncados, caracteres no interpretables o pesos superiores a 100 KB deben ser capturadas por el manejador de solicitudes antes de llegar a la lógica de negocio, respondiendo con HTTP `400 Bad Request` o HTTP `413 Payload Too Large` bajo la estructura estándar JSON `{ "mensaje": "..." }` sin filtrar volcados de memoria, trazas de depuración ni páginas por defecto en HTML. En subidas de archivos multimedia, si una petición falla a mitad del proceso (por ejemplo, un segundo archivo no válido tras haberse escrito el primero en disco), el sistema debe eliminar de forma inmediata cualquier archivo parcial escrito para evitar la acumulación de archivos huérfanos.
4. **Orígenes web maliciosos o no registrados frente a CORS**:
   - Solicitudes que incluyan cabeceras `Origin` no coincidentes con los dominios autorizados en `FRONTEND_URL` deben responder de manera unívoca con HTTP `403 Forbidden` en formato JSON `{ "mensaje": "Acceso denegado por política de origen (CORS)." }` sin exponer encabezados `Access-Control-Allow-Origin` ni reflejar el origen atacante. Al mismo tiempo, las herramientas de automatización de pruebas, peticiones server-to-server o clientes de consola que no emiten cabecera `Origin` deben operar normalmente para facilitar la verificación continua.
5. **Fallos del servicio de mensajería (SMTP) durante la confirmación de compras**:
   - Si tras completarse exitosamente la transacción en base de datos el servicio externo de correo presenta indisponibilidad o latencia, el sistema debe garantizar la resiliencia del proceso: la compra debe persistirse, la factura en Base64 debe retornarse al cliente web para visualización inmediata, y la excepción de transporte de correo debe registrarse como advertencia en los registros sin generar una respuesta HTTP `500` que desoriente al comprador.
6. **Consistencia de estado en productos y catálogo (`Productos.estado` vs `stock = 0`)**:
   - La condición de producto agotado se rige exclusivamente por `stock = 0`. El campo de visibilidad en base de datos conserva siempre su tipo numérico (`1` para activo/visible, `0` para inactivo) y queda estrictamente prohibido mutarlo a cadenas de texto (como `'agotado'`) o forzarlo automáticamente a `0` ante stock nulo. De esta forma se previene corrupción de tipos y el catálogo puede continuar mostrando la ficha informativa del cosmético con el botón de compra deshabilitado por falta de existencias.
7. **Restricción de alcance**:
   - Esta especificación se circunscribe primordialmente a la seguridad, robustez y *hardening* de los servicios backend y su contrato de comunicación con el frontend. Se mantiene intacta la identidad visual "Rose Noir & Gold", la navegación accesible y las vistas aprobadas en la Especificación 002, permitiéndose como única modificación en el cliente web la alineación de la regla de validación de contraseñas en `RestablecerPassword.js` (mínimo 8 caracteres, al menos una mayúscula y un número) para total consistencia con `Registro.js` y con los requisitos de la API.

## 4. Criterios de Aceptación

- [ ] Todas las respuestas emitidas por la API incluyen cabeceras HTTP de seguridad (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Resource-Policy: cross-origin`) y ninguna respuesta divulga cabeceras de huella tecnológica como `X-Powered-By`.
- [ ] Peticiones con cabecera `Origin` no incluida en `FRONTEND_URL` reciben unívocamente HTTP `403 Forbidden` con JSON `{ "mensaje": "Acceso denegado por política de origen (CORS)." }` y sin cabecera `Access-Control-Allow-Origin`, mientras que orígenes autorizados y solicitudes legítimas sin cabecera `Origin` se procesan con normalidad.
- [ ] Los puntos de entrada públicos de autenticación (`/api/auth/login`, `/api/auth/registro`, `/api/auth/recuperar-password`, `/api/auth/restablecer-password/:id/:token`) bloquean el tráfico excesivo con HTTP `429 Too Many Requests` y formato JSON `{ "mensaje": "..." }` al superar el límite estricto de 15 solicitudes en una ventana de 15 minutos por dirección IP, permitiendo la ejecución aislada en `NODE_ENV === 'test'`.
- [ ] Cuerpos de petición JSON mayores a 100 KB reciben HTTP `413 Payload Too Large` JSON; cuerpos JSON malformados reciben HTTP `400 Bad Request` JSON; archivos mayores a 2 MB reciben HTTP `413 Payload Too Large` JSON; solicitudes con más de 3 archivos o formatos distintos de JPEG, JPG, PNG o WEBP reciben HTTP `400 Bad Request` JSON; y cualquier archivo parcial escrito en disco ante fallas de subida es eliminado de inmediato, sin exponer jamás trazas internas ni HTML.
- [ ] La creación de órdenes de compra vincula obligatoriamente la identidad del usuario a la sesión decodificada del token JWT, ignora cualquier identificador de usuario provisto en el cuerpo de la petición, consulta los precios autoritativos vigentes en base de datos y recalcula el importe total en el servidor (*anti-price tampering*).
- [ ] La solicitud de intención de pago en `/api/pagos/crear-intencion` valida que el importe total sea un valor numérico finito estrictamente mayor a 0, rechazando valores inválidos o negativos con HTTP `400 Bad Request` en formato JSON.
- [ ] La insuficiencia de existencias para cualquier producto de la orden responde unívocamente con HTTP `409 Conflict` en formato JSON `{ "mensaje": "..." }`, y el pedido se procesa bajo una única transacción de base de datos atómica que revierte ante cualquier fallo e impide existencias negativas.
- [ ] La condición de producto agotado se representa exclusivamente mediante `stock = 0`, conservando la columna `estado` su valor numérico (`1` activo, `0` inactivo) sin mutar a cadenas de texto ni ocultarse automáticamente.
- [ ] Las rutas de registro, confirmación de restablecimiento y solicitud de recuperación de contraseña validan presencia y formato de datos con HTTP `400 Bad Request` JSON antes de consultar la BD (incluyendo exigencia de al menos 8 caracteres, una mayúscula y un número para contraseñas, y respuesta `200` genérica en recuperación solo ante correos con formato válido para evitar enumeración).
- [ ] La vista `RestablecerPassword.js` del cliente web sincroniza su validación de contraseña con las reglas de seguridad (mínimo 8 caracteres, al menos una mayúscula y un número).
- [ ] Todo dato de usuario interpolado en correos salientes (bienvenida de empleado, recuperación y facturación) es debidamente escapado contra inyecciones HTML, y los enlaces de recuperación emplean el origen configurado en `FRONTEND_URL`.
- [ ] Toda petición a rutas protegidas con token faltante, malformado o expirado recibe unívocamente una respuesta con código HTTP `401 Unauthorized` y formato JSON `{ "mensaje": "..." }`.
- [ ] El archivo `server/.env.example` contiene todas las variables de entorno necesarias documentadas (`PORT`, `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_PORT`, `JWT_SECRET`, `STRIPE_SECRET_KEY`, `EMAIL_USER`, `EMAIL_PASS`, `FRONTEND_URL`, `NODE_ENV`) sin exponer credenciales reales, y el arranque de la API audita y exige la presencia de `JWT_SECRET` y credenciales de BD en entornos operativos.
